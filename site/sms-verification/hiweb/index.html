How to Request a Number via the SMS Verification API

Requesting a number is just a matter of calling the request endpoint with a couple of parameters: the target app (say, WhatsApp) and the country code you want. The API responds with a unique number ID and the actual phone number, which you then feed into the app's verification form. You can request numbers for hundreds of services, and each request is tied to a specific app to ensure the OTP routes correctly.

Here's what you need to know about the request payload:

  • App ID: Specify the service you're verifying for (e.g., whatsapp, telegram, google).

  • Country code: Optional but recommended; use us, uk, in, or any supported ISO code for geo-targeted numbers.

  • Response fields: You'll get number_id (a unique identifier) and number (the actual phone number).

  • Parallel requests: Request multiple numbers simultaneously for load testing or multi-account verification.

  • Holding window: Numbers are held for a default period; extend it with rental options if needed.

A practical tip: always pass the app ID explicitly. If you request a generic number without specifying the app, the OTP might not route correctly. The API is smart about matching numbers to services, but being explicit removes any ambiguity. And if you're testing across regions, request numbers from different country pools to simulate real user behavior. How to Poll for SMS Status with the SMS Verification API

Once you've got a number, you're not done; you need to wait for the code. This is where polling comes in. You hit the status endpoint with your number ID and check if the OTP has arrived. The API returns a status field like PENDING, RECEIVED, or EXPIRED along with the SMS text once it lands. Polling is lightweight and designed for frequent calls, so you can build a tight loop that grabs the code the moment it arrives.

Here's how to structure your polling logic:

  • Use the number_id from the request response in every poll call; this ties the query to the right number.

  • Poll every 2–3 seconds for a snappy user experience; the API handles high-frequency calls without rate limiting.

  • Parse the SMS text from the response; the code is usually in the first few characters or a clear pattern.

  • Handle EXPIRED status by releasing the number and requesting a fresh one if the window lapses.

  • Consider webhooks if you prefer push notifications over polling; the API supports callback URLs.

The key to a smooth experience is a tight loop. If you poll every 5 seconds, you might miss the code window on apps that expire OTPs quickly. At 2–3 seconds, you'll catch the SMS within moments of arrival. And if you're building this into a larger system, the JSON response is structured so you can extract the OTP with a simple regex or string match. For more advanced use cases, the API also supports webhook-style callbacks if you prefer push over poll.

How Fast Is SMS Delivery on the SMS Verification hi web?

SMS delivery is typically fast; most codes arrive within 5 to 30 seconds after the app sends them, depending on the carrier and the app's own SMS routing. The API is designed for near-real-time polling, so you can catch the code as soon as it lands. Here's the timing breakdown you should expect:

  • Polling every 2–3 seconds ensures you catch codes quickly without missing the window.

For a smooth experience, don't assume instant delivery. Build your integration to poll for at least 60–90 seconds before giving up.
